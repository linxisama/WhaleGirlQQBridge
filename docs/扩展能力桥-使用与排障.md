# 扩展能力桥：使用与排障

面向两种人：装完控制台要自己动手的用户，以及以后接手这套代码的维护者。只写能查证的东西——每个数字与行为都给出源码位置或实测命令输出；写不出证据的一律放进每节末尾的「不确定」条目，而不是编一个说法。

实测环境：Python 3.12.10、Node v24.20.0、Windows；本仓库不是 git 仓库，测试用 `python -m unittest`（本机没有 pytest）。

## 1. 三种扩展来源，三种落地位置

| 来源 | 落地位置 | 谁负责落地 | 是否执行第三方 JS |
| --- | --- | --- | --- |
| 市场 zip | `<data>/qqagent_extensions/<id>` | `src/extension_registry.py:56` `market_extensions_dir()`（只算路径，不解压） | 桥不去解压，只有解压到宿主根后才会被 host-one 加载 |
| 宿主根 | `<host_root>/plugins/<id>` | `src/qqagent_host.py:540` `install_extension()`、`:809` `install_market_extension()` | 是（真 `import()` 扩展 index.js） |
| 手写 profiles | 用户自己给的 `extensionPath`（目录或 zip） | 用户 | 是（同上） |

宿主根的准备入口（幂等）：

- `src/qqagent_host.py:388` `ensure_host_root(target=None, source=None, node=None, smoke=True)`：复制后真跑一次 import 冒烟，返回 `{ok, root, copied, skipped, smoke, error}`。
  实测（`.tmp/wp7a/probe.py`，目标为临时目录）：第一次 `{"ok": true, "copied": 272, "skipped": 0, "smoke_ok": true}`，`smoke.node` = `C:\Program Files\nodejs\node.EXE`；第二次同目标 `{"ok": true, "copied": 0, "skipped": 272}`（幂等）；`host_root_stats()` = `{"files": 272, "bytes": 4110639}`（`src/qqagent_host.py:211`）。

### 1.1 为什么 `T4-host-source` 类扩展必须落在宿主根

这类扩展的源码里有 `require('../../src/config.js')` 级别的相对导入（市场侧统计：231/512 = 45.1%，`.tmp/inv/bridge-gap.md:265`）。host-one.mjs 的做法是把扩展复制到 `<source>/plugins-host-<pid>/_compat_one` ——恰好两层深，于是 `../../` 指向 0.4 源码根（同上）。因此：

- `hostScript` 与 `sourceDir` 必须指到「有 `src/config.js` + `src/plugin-loader.js`」的宿主根（`src/qqagent_host.py:80` `host_root_problems()`、`:90` `is_host_root()`）。
- 随便塞进一个只有扩展目录、没有 0.4 源码的路径，这类扩展在 `import()` 阶段就失败，表现为账本里 `ok=false`、`error` 带 `ERR_MODULE_NOT_FOUND`。
- 兼容层自己的 tier 判定把这类扩展标成 `T4-host-source`（`src/extension_registry.py:36-37` 的 tier 名单、`:371-375` 的判定分支：`host_imports` 非空即 `blockers=['host-source']` → `T4-host-source`）。

### 1.2 手上已有 zip：从本地安装

市场里没有、或者你手上的包比市场新时，走这条唯一入口，别手工往 `plugins/` 里塞（手工塞进去 registry 不知道它，桥会当它不存在）。

- GUI：扩展管理 → 右上「从本地 zip 安装…」（`qq_gui.py:3908` 按钮、`:4120` `_import_local_zip`）→ 预检 → 确认框里摊开 ID / 名称 / 版本 / 层级 / 阻塞原因 / 文件数 → 再装 → 成功后刷新列表。
- 端点：`GET|POST /api/extensions/inspect-local`（`src/qq_app.py:4709`）、`POST /api/extensions/install-local`（`:4731`）。

预检是**只读**的：实测在空的临时 data 目录上调用 `_inspect_local_zip`，返回后该目录仍然为空；不 materialize 宿主根、不动 registry、不解压到磁盘。返回键：`['blockers','bytes','declared','description','duplicate','entry','existing','files','id','kind','name','note','ok','path','problems','tier','version']`，样例（`.tmp/external-market/account-appearance.zip`）：
`{"ok": true, "id": "account-appearance", "name": "账号形象参考", "version": "1.1.0", "tier": "T4-host-source", "blockers": ["host-source"], "problems": [], "files": 4, "bytes": 118353, "existing": false, "entry": "index.js"}`。

读这个响应要注意三点：

1. `ok=true` 只表示「包结构与清单合法、能装」，**不表示「装了会生效」**：`blockers` 非空（如上例 `host-source`）的包照样能装进宿主根，但 registry 会按层级把它登记为停用，要你自己确认后再启用。
2. `existing=true`（同时 `duplicate=true`，message 追加「，宿主根里已有同 id，覆盖安装要 force」）表示宿主根里已有同 id。此时**不带 `force` 的安装会直接 400**（detail 前缀「扩展包没装进宿主运行时：这个扩展已经装过：…（exists）」），宿主根与 registry 的 `updatedAt` 都不变；要覆盖必须传 `force=true`，覆盖是整目录替换（写 `.install-<uuid>` → rmtree 旧目录 → os.replace）。
3. `problems` 是提示（人能看懂的原因），不是拦截条件；真正的拦截看 `ok`。

安装端点要求 `confirmed=true`（否则 400「未经确认」），并且**装不进宿主根就直接 400**，不会回退成「zip 留在市场目录」—— 那样 `../../src/*.js` 解析不到，装了也等于没装。路径解析在 `src/qq_app.py:2733` `_resolve_local_zip`：绝对路径、相对程序目录的路径、`<data>/qqagent_extensions/<文件名>` 三种写法都认。

装上 ≠ 能跑：安装端点在装完之后会真加载一次（`import_probe`）。**探测没过（`probe.ok=false`，例如顶层就抛的 `index.js`）时，即使传了 `enable=true` 也按停用登记**，回包 `enabled=false`、note 与 message 都带上「宿主加载探测失败：<原因>」，不会留下一条「每次调用都失败」的白名单。判定只有一份（`src/qq_app.py` `_enable_after_probe`），市场端 `/api/qqagent/market/install`、扩展管理端 `/api/extensions/install`、本地 zip 端 `/api/extensions/install-local` 三条路由共用；没有探测信息（`legacy=1` 只下载）时不改判启用状态。

安全边界：这些本地端点与 `/api/plugins/install-local` 同一模型 —— **无鉴权，信任本机回环**。控制台 API 不要监听公网地址，也不要在多人共用的机器上把它当服务跑。

### 3.1 三个派生函数，先看顺序再填路径

## 4. 三个可观测点

### 4.1 `bridge_status()`

- 模块级 `src/extension_host.py:356` `bridge_status(data_dir, enabled_extensions, limit_errors=5)`：从账本聚合计数的底层实现。
- 插件方法 `src/plugins/qqagent_bridge.py:1455` `bridge_status()`：在底层结果上加 `capabilities`（每条 profile 的 `{extensionId, kind, capability, event, deadInHost}`）、`paths` 与 `list_rows`（`kind='list'` 的枚举行数，口径见 §4.2）。
- `deadInHost` 由 `:1631-1635` 计算：白名单里有、但本仓库没有消费点的 provider 才为 true，判据是 `HOST_CONSUMED_PROVIDERS = {'message.gate', 'message.privilege-check', 'message.identity'}`（`:89-90`）的反面。这三项自 WP14 起都有真实消费点，故现在恒为 false；将来新增白名单 provider 而忘了接消费点，它会重新变 true。
  - `message.gate` → `src/qq_app.py:1870`（入口 `src/plugins/qqagent_bridge.py:1246`）：**fail-open**，只认返回 `{block:true}` 或 `{skip:true}`；挡下时写 `decision()` 审计并把 inbox 置 `state='blocked'`。
  - `message.privilege-check` → `src/qq_app.py:734`（入口 `:1310`）：**fail-closed，且默认整条不派发**。桥设置 `privilegeEscalation` 默认 false，此时 `privilege_allow()` 直接返回 `allow=False`（不起进程、不写账本）；打开后也只认 `allow is True`，且调用点排在"原本就是主人"判定之后，扩展无法把主人降级。
  - `message.identity` → `src/qq_app.py:1898`（入口 `:1278`）：**fail-open 到原值**，只接受 `selfId`/`nickname`/`persona` 三个标量键（`:598`），函数值与其他键一律忽略。

实测（`.tmp/wp7a/probe.py`，空账本的临时 data 目录）：

~~~json
{"provider_calls": 0, "hook_calls": 0, "tool_calls": 0, "list_rows": 0, "calls": 0,
~~~

### 4.2 调用账本 `<data>/qqagent_bridge_calls.jsonl`

- 文件名与轮转阈值：`src/extension_host.py:40` `LOG_NAME`、`:41` `LOG_MAX_BYTES = 8 * 1024 * 1024`。超过阈值时改名为 `.jsonl.1`（`:324-326`），只保留一代。
- 写入口 `_record()`（`:311`）在每次 provider/hook/tool/枚举调用后追加一行；写日志本身失败绝不影响调用（`:329` 捕获 `OSError`）。
- 读入口 `read_log()`（`:333`）只读文件尾部，默认 4000 行。

字段含义：

| 字段 | 含义 |
| --- | --- |
| `ts` / `time` | Unix 秒（3 位小数）/ 本地时间 `%Y-%m-%dT%H:%M:%S` |
| `kind` | `provider` / `hook` / `tool` / `list`（枚举；见 `qqagent_bridge.py:1224`） |
| `extension` | 扩展 id（`_extension_id()` 解析，`:550`） |
| `capability` | provider 名 / hook 名 / 工具全名 |
| `ok` / `timed_out` | 成功与否 / 是否超时被杀 |
| `duration_ms` / `timeout_s` | 实测耗时 / 本次生效的超时上限 |
| `path` | `async`（`_stage`，`:916`）或 `sync`（`_stage_sync`，`:929`）或 `sweep` |
| `pid` | 子进程 pid（进程隔离的实证） |
| `error` | 错误摘要，截断到 200 字符 |

真实样例行（一次 before-tool 派发，search-tuner）：

~~~json
{"ts": 1792926305.947, "time": "2026-10-25T19:05:05", "kind": "hook", "extension": "search-tuner",
 "capability": "before-tool", "ok": true, "timed_out": false, "duration_ms": 140,
 "timeout_s": 20.0, "path": "async", "pid": 18144, "error": ""}
~~~

计数口径（WP13 已解决）：`calls` 仍是**账本总行数**，包含 `kind='list'` 的枚举行；要"真实派发次数"请看 `provider_calls`/`hook_calls`/`tool_calls`（各自只统计自己那一种派发，`src/extension_host.py:370-375`），枚举行单独记在新增的 `list_rows` 上，恒等式 `calls = provider_calls + hook_calls + tool_calls + list_rows`。新增字段只出现在 `bridge_status()` 的返回体里，`calls` 原值不动，也不另造一套同义键（没有 `hookCalls`/`listRows` 这种 camelCase 双份）。

实测（`.tmp/wp13-scratch/probe_wp13.py`，同一次操作前后）：3 次工具枚举 + 1 次 search-tuner before-tool 真派发 → 加字段前 `{"provider_calls": 0, "hook_calls": 1, "tool_calls": 0, "calls": 4}`（把 `calls` 当调用次数就会误导）；加字段后 `{"provider_calls": 0, "hook_calls": 1, "tool_calls": 0, "list_rows": 3, "calls": 4}` —— `calls` 没变，4 = 0+1+0+3 对得上，误读不再可能。

## 5. 排障决策树

### 5.1 「扩展装了，但一点反应都没有」

按顺序排查，每一步都有可执行命令：

1. **桥本身开着吗**：`bridge_status()` 里 `enabled` 对应的设置项是 `enabled`（`:747`）。关着时任何面都不起进程（`list_tools()` 回 `[]`，`call_tool()` 回 `kind='disabled'`，实测 `{"ok": false, "error": {"kind": "disabled", "message": "bridge disabled"}}`）。
2. **registry 启用了吗**：
   ~~~bash
   python -c "from src import extension_registry as r; print(r.is_known('search-tuner'), r.is_enabled('search-tuner'))"
   ~~~

   已登记且 `enabled=false` 时，工具面与钩子面**都不派发**（`_registry_disabled` `:807`，用例 `tests/test_qqagent_bridge_gate.py:78` 与 `:134`）。

### 5.2 「工具在列表里，但模型一调就错」

## 7.1 扩展间依赖（requires）怎么加载

第二轮补上的能力：`host-one.mjs` 会按 `requires` 递归装载能力提供者，**依赖表只认 registry 的已启用集合**，不由桥或运行器自己猜。

四个可 grep 的锚点：

- `src/extension_host.py:196 _child_env(source_dir, extra, data_dir=None, timeout=DEFAULT_TIMEOUT)` 给每个子进程注入 `QQ_AGENT_DEPENDENCY_IDS = json.dumps(extension_registry.enabled_ids(data_dir))`；registry 缺失/损坏时返回 `[]`，**绝不回退到"全开"**。
- `src/extension_host.py:192 INHERITED_ENV_BLOCKLIST = ('QQ_AGENT_CTX', 'QQ_AGENT_DEPENDENCY_IDS', 'QQ_AGENT_HOST_TIMEOUT_MS')`：父进程的同名变量一律剔掉，陈旧值不能污染子进程（见 C10）。
- `runtime/qqagent-host/host-one.mjs:152-163` 解析能力：`dependency-cycle` / `dependency-missing` / `dependency-disabled` / `dependency-ambiguous`（同名能力有多个已启用提供者）。
- `runtime/qqagent-host/host-one.mjs:195` 在隔离根写 `.whale-host-one-owner.json`；`src/extension_host.py:212 _cleanup_isolated_roots(source_dir, pid)` 只删 pid 与 source 都对得上的 `plugins-host-<pid>`，别的进程的目录不动（见 C21）。

实测（`.tmp/accept/dep_e2e.py`，真 `ensure_host_root` 272 文件 + 真装 zip + 真 node）：

- `coin-reward` 需要 `currency.v1`，提供者 `currency`：registry 启用 currency → 加载成功，`dependencies=['currency']`，工具 `coin-reward__checkin` / `coin-reward__reward_status`。
- 把 currency 停用 → `ok=False`、`error.code=dependency-disabled`、文案「coin-reward 的依赖未启用：currency.v1（currency）」。
- `keyword-reply` 需要 `command.dispatch`，提供者 `command-gateway-1.7.0`：即使把 gateway 登记为启用，仍然 `dependency-disabled / 宿主配置未启用：command-gateway-1.7.0` —— **依赖机制到位，不等于提供者能跑**。

全市场需要依赖的消费者共 10 个，涉及 3 个能力名：`currency.v1`（currency，P1）、`command.dispatch`（command-gateway-1.7.0，P3）、`memory-star.nodes`（memory-star，P3）。今天真正跑通的是 `currency.v1` 这一条链。

查数据时的坑：`requires` 在 `.tmp/inv/plugin-tools.json` 里位于 `declared.requires` / `signals.requires`，顶层没有这个键（按顶层查会得到 0 个）。

## 10. 双向 MCP：出去走工具桥，进来走导入 + 工具环

两个方向是两套代码，互不依赖：

- **出去**：`tools/whale_tools_mcp.py` 把自己当 MCP 服务端（stdio），把本机的扩展工具与技能工具交给外部 agent（DSH 桌面版就是这样一个客户端）。
- **进来**：`src/pack_import.py`（认包 + 落盘 + 登记）与 `src/mcp_tools.py`（懒启动 + 调用）把外部 MCP server 的工具并进本机工具环。

两边的调用账本落在**同一个文件** `<data>/qq-only/mcp_tool_calls.jsonl`，靠 `client` 列区分来源。

### 10.1 出去：三个元工具 + 写闸门 + 审计

stdin/stdout 走 JSON-RPC 2.0，手写实现、不引第三方（venv 里没有 `mcp` 包）；`serverInfo` = `whale_tools` 1.0.0，`protocolVersion` 默认 `2025-06-18`（`tools/whale_tools_mcp.py:29-31`）。两个方向都锁成 UTF-8（`force_utf8_stdio()` `:62-76`）——中文 Windows 默认 cp936，对端按 UTF-8 解析就会失败，DSH 侧只表现为 server unavailable。

对外只有三个元工具，工具清单本身也走它们（`tools/whale_tools_mcp.py:94-115`、`:405`、`:433-434`）：

| 元工具 | 作用 | 参数 |
| --- | --- | --- |
| `tools_list` | 列可用工具 | `filter`（在 id / extension / description 里做子串匹配）、`write`（true 只看写、false 只看只读）、`limit`（默认 200，上限 500，`:42`、`:355-357`）、`refresh` |
| `tools_call` | 调一个工具 | `tool`（必填）、`arguments`、`confirm` |
| `tools_status` | 体检：node / 宿主脚本 / 源码树 / 计数 / 审计落点 / 写工具清单 | 无（`:112-114`、`:246-266`） |

工具 id：扩展工具一律 `<extensionId>__<toolId>`（`:164-170`），技能工具直接沿用 `src/skill_tools.eligible_skills()` 已经算好的 `<skillId>__<tool>`（`:189-193`）。条目里的 `enabled` 有两种含义：扩展工具恒 `true`（`:146-148`）；技能工具表示这个技能有没有装到 `<data>/qq-only/skill_extensions/<id>`（`:43`、`:181`、`:194`），没装时调用回 `not-installed`（`:319-321`）。找不到 node 回 `node-missing`（`:322-325`）。

写操作集合是一个写死的常量 `WRITE_TOOLS`（`tools/whale_tools_mcp.py:54-59`），由三处来源拼起来（`:45-49` 的注释写明出处）：`DANGEROUS` 六项（`service` / `open_path` / `open_url` / `type_text` / `hotkey` / `screenshot`，`:50`）、工作区写（`write` / `append`，`:51`）、`pc_` 前缀里除 `PC_CONTROL_READONLY` 三个（`pc_status` / `pc_active_window` / `pc_clipboard_read`，`:53`）以外的全部 pc 工具。判定入口 `is_write()`（`:79-91`），`<extId>__<toolId>` 与裸 toolId 两种写法都认。

写工具在 `tools_call` 里必须带 `confirm: true`，否则**不执行**、直接回 `confirm-required`（`:388-392`，提示文案在 `:36`）；只读工具不看 `confirm`。闸门只针对被调的那个工具，不针对元工具本身。

每次 `tools_call`（成功、失败、`confirm-required` 都算）都追加一行审计 `<data>/qq-only/mcp_tool_calls.jsonl`（`:270-271`），固定 8 个字段（`:277-279`）：

~~~json
{"ts": 1761234567.891, "tool": "search-tuner__search", "write": false, "confirm": false, "ok": true, "code": "", "duration_ms": 42, "client": "deepseek-harness"}
~~~

`ts` 是 epoch 秒（三位小数）；`code` 只在失败时非空；`client` 取 `initialize` 里的 `clientInfo.name`（截 80 字，`:419-421`）。文件超过 8MB（`:35`）就先改名成 `mcp_tool_calls.previous.jsonl` 再写新的（`:283-284`）——只留一份历史，不是多份滚动。审计写不进去只是回包里 `audited=false`，调用本身不算失败（`:274-275`、`:344`）。

数据目录四级优先（`:456-471`）：`--data-dir` 显式参数 > 环境变量 `WHALE_TOOLS_DATA_DIR` > `WHALE_QQ_HOME` 目录下的 `data/` > 仓库 `data/`（`extension_host.default_data_dir()`，`src/extension_host.py:576-578`）。DSH 那条登记传的是 `WHALE_QQ_HOME`（`src/dsh_memory_bridge.py:84`），所以从 DSH 侧看到的是 `<WHALE_QQ_HOME>/data/qq-only/mcp_tool_calls.jsonl`；漏认这个变量会静默写到默认 `data/`（`tools/whale_tools_mcp.py:38-40` 的注释）。

重复执行是幂等的：内容没变就**不落盘**，回 `{"changed": false, "backup": null}`（`src/dsh_memory_bridge.py:130-135`）；真变了才备份，文件名 `<原文件>.bak-whale-memory-<YYYYmmdd-HHMMSS>`（`:28`、`:107-110`），所以跑两遍不会多一份备份。

### 10.3 进来：导入外部 MCP 包，工具并进工具环

导入对话框认 `mcp.json`，家族名「MCP 服务」（`src/gui/import_dialog.py:54`，配色在 `:62`）；在识别内核里是第五种家族 `mcp-server`（`src/pack_import.py:44-45`）。

两种形状都认（`_mcp_server()` `:377-390`）：

~~~json
{"mcpServers": {"my-server": {"command": "python", "args": ["server.py"], "env": {}}}}
~~~

~~~json
{"command": "python", "args": ["server.py"]}
~~~

`mcpServers` 里有多条时**只导入按名字排序的第一个**，并在卡片上给一条 notice「本包含 N 个 MCP server，只导入 X（其余 N-1 个没动）」（`:726-730`）。找 `mcp.json` 会往下钻，最多 4 层目录，取最浅的那个（`DRILL_LIMIT = 4` `:51`，`_find_mcp()` `:355-366`）。包根已经摆着 `pack.json` / `skill.json` / `plugin.json` 时不让 mcp 分支抢（`:253`）。

只有 `url` / `sse` 的包**仍然被认成「MCP 服务」**，不会掉进"认不出来"：预检阶段给一条 problem，`code=unsupported-transport`，提示原文「目前只支持 stdio（command/args），HTTP/SSE 型 MCP server 暂不支持」（`src/pack_import.py:748-754`，常量在 `:60`）——家族认对了，只是装不上。`command` 是相对路径也拦（`command-not-absolute`，`:755-759`）；是裸可执行名（例如 `node`）只提示运行时要靠 PATH（`command-on-path`，`:760-763`）。

落盘两处：

- 包体：`<data>/qq-only/mcp_servers/<id>/`（`src/pack_import.py:57`、`:741-742` 的 `target_dir`）。
- 登记表：`<data>/qq-only/mcp_servers.json`，形状 `{"version":1,"servers":[...]}`（`:58`、`:1547-1569`），每条 9 个字段（`:1534-1544`）：`id` / `name` / `command` / `args` / `env` / `cwd`（落盘时折成绝对路径，`:1530-1540`）/ `enabled`（导入时写死 `true`）/ `source_package` / `installed_at`。

同 id 再导一次是**就地覆盖那一条**、不追加第二条（`:1560-1564`）；目标目录已存在且没传 `overwrite` 时预检就报 `exists` 并停（`:1585-1589`）。没有 `data_dir` 直接报 `no-target`，本模块不会回落到仓库 `data/`（`:1574-1578`）。

这些 server 的工具由 `src/mcp_tools.py` 并进工具环：

- 工具名 `<serverId>__<toolName>`，清洗成 `^[a-zA-Z0-9_-]{1,64}$`、过长截断、撞名挂 `_2` 后缀（`src/mcp_tools.py:11-12`、`:36-39`、`:65-75`）。
- 懒启动 + 进程内复用：登记表在 import 期只当 JSON 读，只有真要 `tools/list` / `tools/call` 时才起子进程，同一个 server 复用同一条管道（`:5-7`、`:263-292`）。
- `enabled` 必须是 JSON 里的布尔 `true` 才算启用，缺字段按停用（`:179-180`）。
- 某个 server 起不来只把它标成 `unavailable`（起不动 / 握手超时）或 `error`（起来了但列不出工具），从清单里缺席；别的 server 与内置工具都不受影响（`:41-42`、`:222-226`、`src/skill_tools.py:1076-1081`）。
- 进 `eligible_skills()` 的两个位置不一样：顶层键 `mcpTools` **恒存在**（没装外部 server 时是空列表，`src/skill_tools.py:869-870`）；`counts['mcpTools']` 只在有外部工具时才出现，同时把原来的 `counts['tools']` 存进 `counts['skillTools']` 再相加（`:861-868`）。
- 注册进工具环在 `register_skills()` 里按 server 分组做：先 `unregister_source(server_id)` 再 `register_tools(...)`，重复注册不会攒出 `__2` 后缀（`src/skill_tools.py:1232-1267`）。

外部调用的审计也落 `<data>/qq-only/mcp_tool_calls.jsonl`，同样 8 字段、同样 8MB 转 `.previous.jsonl`，但有两处和工具桥不同（`src/mcp_tools.py:388-410`）：

- `client` 固定写 `mcp-client`（`:31`），拿它跟工具桥的行区分。
- **外部调用没有 confirm 闸门**：`confirm` 恒 `false`；`write` 只是按工具名里的动词猜出来的 `write_hint`（`WRITE_TOKENS` `:48-52`、`write_hint_of()` `:78-81`），猜错不影响调用，也不是安全边界——要拦外部工具的写操作，只能在那个 server 自己的实现里拦。

导入后去哪看结果、去哪看审计：

1. 导入对话框的预检卡片：家族显示「MCP 服务」，能看到 id、`target_dir`，以及 `tools-at-runtime` / `multiple-servers` 这类 notice（`src/pack_import.py:733-742`、`:726-730`）。MCP 包的 `tools` 恒为空——要等 server 起来才知道有哪些工具（`:736-738`）。
2. 落盘结果：

### 10.4 排障三连

**A. DSH 里看不到 `mcp__whale_tools__*`**

1. `python tools/setup_dsh_memory.py --status`：`tools_installed` 要是 `true`、`tools_timeout_ms` 要是 30000、`tools_utf8_env` 要是 `true`（`src/dsh_memory_bridge.py:160-166`）。是 `false` 说明第三条没写进去，重跑一次登记（别带 `--no-tools` / `--bot-only`）。
2. 是不是改了配置但**没退出桌面版**：MCP client 只在建会话 scope 时拉一次，不重试、不热加载（`tools/setup_dsh_memory.py:14-16`）。
3. 桥自己能不能跑：`python tools/whale_tools_mcp.py --list` 看 `node` / `hostScript` / `sourceDir` / `counts` / `errors`（`:246-266`、`:500-501`）。`errors` 里 `extension:` 前缀 = 宿主根读不出来，`skill:` 前缀 = 技能清单读不出来（`:156`、`:179`）；两类都只让各自来源缺席，桥照常应答。

**B. 导入说认不出来 / 装不上**

1. 包根是不是已经有 `pack.json` / `skill.json` / `plugin.json`：有的话 mcp 分支让路，按那三种家族判（`src/pack_import.py:253`）。
2. `mcp.json` 是不是埋太深：超过 4 层目录就不找了（`:51`、`:360`）。
3. 是不是只有 `url` / `sse`：报 `unsupported-transport`（`:748-754`）——家族认对了，只是现在拉不起来。
4. 是不是 `mcpServers` 里有多个 server：只导排序第一个（`:726-730`），其余要拆成单 server 的包再导。
5. 是不是相对 `command`：报 `command-not-absolute`（`:755-759`）。

**C. `tools_call` 回 `confirm-required`**

1. 这个工具在 `tools_list` 里 `write:true` 吗？是写工具就必须带 `confirm: true`（`tools/whale_tools_mcp.py:388-392`）。
2. 参数名对不对：`tools_call` 只认 `tool` / `arguments` / `confirm`，多给一个键直接 `invalid-argument`（`:443-448`）。
3. 带上 `confirm` 还失败就看 `error.code`：`unknown-tool`（id 打错，`:383-387`）、`not-installed`（技能没装，`:319-321`）、`node-missing`（找不到 node，`:322-325`）、`internal-error`（扩展自己抛了，`:326-331`）。
4. 只读的 `pc_status` / `pc_active_window` / `pc_clipboard_read` 不该要 `confirm`（`:53`）；要了说明 id 被当成写工具了，先核对 id 有没有拼错。

### 10.5 这一节的不确定

- DSH 桌面版里真出现 `mcp__whale_tools__*` 这一步没有在本轮实测（它要求完全退出桌面版再启动，而当时用户正开着 GUI，不许重启）。本节只验到"桥能被 stdio 客户端正常握手、`tools/list` 回 3 个元工具、`tools_call tools_list` 回 153 条"这一层。
- 外部 server 那条链的真实第三方包没跑过："没有外部 server 时既有数字不变"是实测的（见下），登记表读写逻辑是从源码读的。
- 本轮实测（文档侧取证）：无外部 server 时 `eligible_skills()` 的 `counts` 仍是 `manifest=376 / eligible=57 / skipped=319 / tools=153`，`counts` 里**没有** `mcpTools` 键，顶层 `mcpTools` 是空列表；`McpToolProvider(status)["servers"]` = `[]`、`tools` = 0。

### 10.6 改了控制台端口：控制桥怎么跟随

控制桥（`mcp-whale-bot` → `tools/whale_bot_mcp.py`）运行期不写死端口，按 `src/bot_control_api.py:32-45` 解析：`WHALE_BOT_URL` 有值就用它，否则跟 `WHALEGIRL_PORT`，非法值兜底 `http://127.0.0.1:27499`。`tools/setup_dsh_memory.py` 的 `--bot-url` 用同一口径；但它把**登记那一刻**的地址写进 profile，所以改端口后要重跑一次登记——profile 里那条旧 `WHALE_BOT_URL` 会压过 `WHALEGIRL_PORT`，工具调用就打到没人监听的端口。

情形一 · 同机只改端口：不写死地址，让登记跟着端口算。

~~~powershell
cd D:/qq机器人5.0; $env:WHALEGIRL_PORT = '28651'; & "D:/聊天机器人/qq机器人/.venv-build/Scripts/python.exe" tools/setup_dsh_memory.py
~~~

情形二 · 跨机 / 跨进程（控制台在另一台机器，或端口自己拿不准）：显式给地址，优先级最高。

~~~powershell
cd D:/qq机器人5.0; $env:WHALE_BOT_URL = 'http://192.168.1.20:28651'; & "D:/聊天机器人/qq机器人/.venv-build/Scripts/python.exe" tools/setup_dsh_memory.py
~~~

核对：跑一次 `--status`，回包里的 `bot_url` 就是写进 profile 的地址；同一次调用里 `--bot-url` 显式参数 > 环境变量。
